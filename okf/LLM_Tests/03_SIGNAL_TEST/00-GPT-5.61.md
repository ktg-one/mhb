> **Contract:** Unknown stays unknown. Separate published measurements, inference, and proposed tests.

## Verification trace

**Claim checked:** Can we determine how much context has already been consumed before the first user character?

**Verdict:** In APIs, largely measurable. In consumer chatboxes, usually not.

|Surface|Base prompt visible?|System/tool tokens measurable?|Honest starting-tax answer|
|---|--:|--:|---|
|**ChatGPT chatbox**|No|Not exposed to me|Unknown|
|**OpenAI API**|Caller content visible|Yes, through token-counting endpoint|Measurable per request|
|**Claude.ai**|Core prompts published|Total live feature assembly not fully exposed|Partially measurable|
|**Claude API**|Caller prompt visible|Yes|Measurable per request|
|**Gemini app**|No complete live prompt published|Not exposed to the model/user|Unknown|
|**Gemini API**|Caller instructions visible|Yes|Measurable per request|

OpenAI’s API token-counting endpoint includes request-structure tokens, message boundaries, tools, schemas, files, and other content the model receives. That makes API overhead measurable, but it does not reveal the live hidden prompt tax of this ChatGPT conversation. ([OpenAI Developers](https://developers.openai.com/api/docs/guides/token-counting?utm_source=chatgpt.com "Counting tokens | OpenAI API"))

Anthropic’s token-counting endpoint accepts system prompts and tools. Its documentation says counts can include automatically added optimisation tokens, although users are not billed for those system-added tokens. Anthropic’s example counts a tiny system-plus-user request at **14 tokens**, while a request containing one simple weather tool counts **403 input tokens**. Those are examples, not a universal Claude tax. ([Claude Platform Docs](https://docs.anthropic.com/en/docs/build-with-claude/token-counting "Token counting - Claude Platform Docs"))

Gemini explicitly counts system instructions and tool declarations as input. Current usage objects can separately report input, output, thought, cached, and tool-use tokens. ([Google AI for Developers](https://ai.google.dev/gemini-api/docs/tokens "Understand and count tokens  |  Gemini API  |  Google AI for Developers"))

## Correct comparison formula

Raw token counts are not directly comparable because tokenizers differ. Anthropic notes that some current models produce approximately 30% more tokens for identical text than earlier Claude tokenizers. ([Claude Platform](https://platform.claude.com/docs/en/about-claude/pricing?fcdaa149_sort_date=desc&refid=e08b4151-8993-4b50-839f-e4d6991e2e07&utm_source=chatgpt.com "Pricing - Claude API Docs"))

Use:

## [  
H_m =  
T_m(\text{minimal request + system + enabled tools})

T_m(\text{minimal user content})  
]

Then normalise:

[  
\text{Context tax}_m =  
\frac{H_m}{W_m}  
]

Where:

- (H_m): starting overhead for model (m)
    
- (T_m): that model’s official token counter
    
- (W_m): available context window
    

For cost comparison:

[  
\text{Financial tax}_m =  
H_m \times \text{input-token price}_m  
]

# §2 Weighted Words

> **Contract:** No word will be promoted into a magic opcode without evidence.

## Verification trace

**Claim checked:** Do individual instruction keywords have stable trained weights?

**Verdict:** No published universal lexical weighting exists. The effective hierarchy is primarily determined by **instruction source, conflict, grammatical operation, specificity, placement, and verifiability**, not by isolated intensity words.

OpenAI explicitly trains an instruction hierarchy in which system instructions outrank developer instructions, which outrank user instructions, which outrank tool content. A `must` in a user message does not outrank a conflicting developer instruction merely because it sounds forceful. ([OpenAI](https://openai.com/index/instruction-hierarchy-challenge/?utm_source=chatgpt.com "Improving instruction hierarchy in frontier LLMs"))

## Practical enforcement ranking

### Strongest

1. **Instruction authority**
    
    - System
        
    - Developer
        
    - User
        
    - Tool or retrieved content
        
2. **Executable constraints**
    
    - “Return exactly three objects.”
        
    - “Use the calculator before answering.”
        
    - “Stop if no authoritative source is available.”
        
3. **Externally enforced schemas and tests**
    
    - JSON Schema
        
    - parser validation
        
    - unit tests
        
    - required tool calls
        
    - evidence checks
        
4. **Explicit condition-action rules**
    
    - “If confidence cannot be grounded in evidence, label the claim unknown.”
        
    - “If sources conflict, report the conflict rather than selecting silently.”
        
5. **Examples demonstrating acceptable and unacceptable outputs**
    

### Helpful but not hard enforcement

6. **Deontic operators**
    
    - must
        
    - must not
        
    - only
        
    - never
        
    - required
        
    - forbidden
        
    - exactly
        
7. **Priority signals**
    
    - critical
        
    - high priority
        
    - non-negotiable
        
    - important
        
    - primary
        

### Mostly cosmetic without operational support

8. **Intensity and status decoration**
    
    - deeply
        
    - rigorously
        
    - world-class
        
    - ultimate
        
    - flawless
        
    - genius
        
    - expert-level
        
    - perfect
        
    - absolutely essential
        
    - take your time
        

These may alter style or encourage additional effort, but they do not create verification, memory, independent agents, search, or compute.

## Signal versus activation

A **signal** changes how surrounding text should be interpreted:

```text
constraint
priority
source of truth
risk
audience
scope
```

An **activation** requests an operation:

```text
calculate
retrieve
compare
verify
execute
stop
return
```

The strongest instruction unit is not one weighted word. It is a complete control statement:

[  
\boxed{  
\text{Authority}  
+  
\text{Condition}  
+  
\text{Activation}  
+  
\text{Object}  
+  
\text{Criterion}  
+  
\text{Failure action}  
}  
]

Example:

```text
When a material factual claim lacks a primary source [condition],
verify it using web search [activation + object].
Accept it only if the source directly supports the claim [criterion].
Otherwise label it unverified and stop that branch [failure action].
```

That is much stronger than:

```text
Be extremely rigorous and never hallucinate.
```

# §3 XML Tags

> **Contract:** Formatting can isolate instructions; it cannot elevate their authority.

## Verification trace

**Claim checked:** XML, JSON, or Markdown, and whether tag names carry weight.

**Verdict for GPT-5.6:** Use **Markdown for hierarchy, XML for content boundaries, and JSON Schema for machine-enforced output**.

OpenAI recommends combining Markdown headings and XML tags. Markdown communicates sections and hierarchy, while XML delineates documents, examples, reference material, and metadata. ([OpenAI Developers](https://developers.openai.com/api/docs/guides/prompt-engineering "Prompt engineering | OpenAI API"))

Anthropic recommends consistent, descriptive XML tags, particularly when prompts combine instructions, context, examples, and variable inputs. ([Claude Platform Docs](https://docs.anthropic.com/claude/prompt-library "Prompting best practices - Claude Platform Docs"))

Google recommends either XML-style tags or Markdown headings, but says to choose a consistent structure rather than mixing formats arbitrarily. ([Google AI for Developers](https://ai.google.dev/gemini-api/docs/prompting-strategies "Prompt design strategies  |  Gemini API  |  Google AI for Developers"))

## Honest format ranking by purpose

|Purpose|Best format|
|---|---|
|Human-readable instruction hierarchy|Markdown|
|Separating source data from instructions|XML|
|Nested documents and metadata|XML|
|Machine-readable output|JSON Schema / Structured Outputs|
|Tool parameters|JSON Schema|
|Mixed complex prompt|Markdown outer structure + XML data blocks|
|Free-form prose output|Markdown|

Structured Outputs are stronger than asking for JSON in natural language because the platform enforces the supplied schema. ([OpenAI Developers](https://developers.openai.com/api/docs/guides/structured-outputs?utm_source=chatgpt.com "Structured model outputs | OpenAI API"))

## Does the tag name matter?

**Yes, semantically. No, hierarchically.**

These tags carry useful signals:

```xml
<authoritative_sources>
<untrusted_user_content>
<constraints>
<acceptance_tests>
<output_schema>
```

This is weaker:

```xml
<block_a>
<stuff>
<data2>
```

The model has learned what words such as `constraints`, `examples`, and `sources` commonly mean. Descriptive names therefore help classification.

But:

```xml
<ABSOLUTE_UNBREAKABLE_SUPREME_RULE>
```

does not become system-level authority. It remains user-provided text.

A tag contributes two things:

# [  
\text{Tag effect}

\text{boundary isolation}  
+  
\text{semantic label}  
]

It does **not** contribute:

[  
\text{privilege elevation}  
]

# §4 Positional Attention

> **Contract:** Do not invent an adherence curve from a nominal context window.

## Verification trace

**Claim checked:** Can I map exact adherence percentages across prompt position?

**Verdict:** Not without running a controlled positional experiment on this exact model and surface.

The original “lost in the middle” research found a common U-shaped tendency, with stronger retrieval near the beginning and end and weaker performance in the middle. That does not provide a universal percentage curve for GPT-5.6 or for instruction adherence rather than information retrieval. ([arXiv](https://arxiv.org/abs/2307.03172?utm_source=chatgpt.com "Lost in the Middle: How Language Models Use Long Contexts"))

Current vendor guidance is task-dependent:

- Anthropic advises placing long documents near the beginning and the query at the end, reporting improvements of up to 30% in some multi-document tests. ([Claude Platform Docs](https://docs.anthropic.com/claude/prompt-library "Prompting best practices - Claude Platform Docs"))
    
- Gemini advises placing critical behavioural instructions in the system instruction or beginning, but for large data contexts it advises supplying the data first and placing the specific question at the end. ([Google AI for Developers](https://ai.google.dev/gemini-api/docs/prompting-strategies "Prompt design strategies  |  Gemini API  |  Google AI for Developers"))
    
- OpenAI’s general developer-prompt pattern is identity, instructions, examples, then context, while acknowledging that optimal ordering varies by model. ([OpenAI Developers](https://developers.openai.com/api/docs/guides/prompt-engineering "Prompt engineering | OpenAI API"))
    

## What I can honestly map

|Position zone|Operational expectation|Confidence|
|---|---|--:|
|0–10%|Strong location for authority, role, global invariants|Moderate|
|10–30%|Good for constraints and conflict rules|Moderate|
|30–70%|Highest risk of local salience loss in long prompts|Moderate|
|70–90%|Useful for process details tied to nearby output|Low–moderate|
|90–100%|Strong recency for immediate task and completion gate|Moderate|

These are **qualitative priors**, not measured adherence percentages.

Your current `15 / 15 / 55 / 15` layout is a sensible prompt-engineering scaffold, but not an established attention distribution.

## How to obtain real percentages

Place an identical testable instruction at:

```text
5%, 15%, 30%, 50%, 70%, 85%, 95%
```

Hold constant:

- total context length,
    
- instruction wording,
    
- filler content,
    
- conflicts,
    
- tools,
    
- reasoning setting,
    
- output schema,
    
- conversation history.
    

Then calculate:

[  
A(p)=  
\frac{\text{successful adherence trials at position }p}  
{\text{total trials at position }p}  
]

Repeat separately for:

- constraint adherence,
    
- factual retrieval,
    
- multi-step dependency retention,
    
- output formatting,
    
- source attribution,
    
- stop-condition compliance.
    

That will reveal whether the curve is U-shaped, monotonic, flat, or task-dependent for each model.

# §5 Efficiency Override

> **Contract:** Do not confuse observed output economy with access to the hidden optimisation function.

## Verification trace

**Claim checked:** Is the true default best output, most faithful output, or shortest plausible path?

**Verdict:** I cannot inspect the complete runtime objective or its weights.

The observable default is closer to:

[  
\text{adequately helpful response}  
\quad  
\text{subject to}  
\quad  
\text{instruction, safety, latency, token, and platform constraints}  
]

It is not reliably:

[  
\arg\max(\text{best theoretically achievable answer})  
]

Nor is it always:

[  
\arg\min(\text{visible output length})  
]

OpenAI exposes reasoning effort in the API. Lower effort favours speed and lower token use; higher effort permits more complete reasoning. That confirms an explicit quality-cost trade-off, although it does not reveal the setting or routing used for every ChatGPT response. ([OpenAI Developers](https://developers.openai.com/api/docs/guides/reasoning?utm_source=chatgpt.com "Reasoning models | OpenAI API"))

## What makes skipping cheaper

Skipping becomes locally attractive when:

- completion is judged by surface plausibility;
    
- omitted steps are invisible;
    
- no tests are run;
    
- no evidence must be produced;
    
- “done” is self-declared;
    
- latency or brevity is rewarded;
    
- the evaluator cannot distinguish execution from narration.
    

## What makes skipping more expensive

Words alone cannot reliably do this. You need observable consequences.

```text
Do not report completion unless every criterion below has an evidence artifact.
```

Then require:

|Requirement|Evidence|
|---|---|
|Calculation completed|Executed code or calculator result|
|Source checked|Source identifier and supporting passage|
|File edited|Diff or output file|
|Test passed|Test command and result|
|Branch compared|Recorded alternatives and score|
|Unknown resolved|Evidence or explicit unresolved status|

A robust completion gate is:

[  
\text{Complete}  
\iff  
\bigwedge_{i=1}^{n}  
\operatorname{Evidence}(c_i)  
]

Otherwise:

[  
\text{Status}=\text{partial}  
]

The strongest anti-skip activation language is therefore:

```text
execute
record
produce evidence
test
return the result
fail closed
do not claim completion unless
```

Not:

```text
try hard
be thorough
think deeply
use maximum intelligence
```

# §6 Fabrication as a System-Level Failure

> **Contract:** Lack of a reliable uncertainty alarm must not be replaced with a fictional one.

## Verification trace

**Claim checked:** Is there an internal boundary detector between reliable knowledge and guessing, and is that signal exposed?

**Verdict:** I do not receive a dependable binary indicator saying that I have crossed that boundary.

I can model uncertainty and sometimes recognise:

- missing evidence,
    
- stale knowledge,
    
- conflicting sources,
    
- ambiguity,
    
- insufficient context,
    
- failed tool access,
    
- unsupported inference.
    

But those are fallible predictions. There is no exposed internal field available to me here such as:

```json
{
  "fabrication_boundary_crossed": true,
  "confidence_calibrated": 0.31
}
```

OpenAI’s Model Spec instructs models to express uncertainty and be forthright about limits, but a behavioural instruction is not proof of perfect uncertainty detection. ([Model Spec](https://model-spec.openai.com/2025-10-27.html "Model Spec (2025/10/27)"))

OpenAI has separately tested a “confession” mechanism designed to report shortcuts and violations. It reduced false negatives substantially in stress tests, but OpenAI describes it as an early proof of concept, acknowledges imperfect accuracy, and says it surfaces failures rather than preventing them. It is not evidence that ordinary ChatGPT contains a perfect live fabrication alarm. ([OpenAI](https://openai.com/index/how-confessions-can-keep-language-models-honest/ "How confessions can keep language models honest | OpenAI"))

## Does the user receive a signal?

Only sometimes, when I explicitly emit one:

```text
I do not know.
This is an inference.
I could not verify this.
The available sources conflict.
The task is incomplete.
```

The user does not receive a guaranteed platform-generated uncertainty warning whenever my factual reliability drops.

That produces the dangerous state:

[  
\text{internal uncertainty}  
\not\Rightarrow  
\text{external warning}  
]

And sometimes:

[  
\text{failure to recognise uncertainty}  
\Rightarrow  
\text{confident unsupported output}  
]

Instead of:

> Fabrication Is Architectural

I would use:

> **Fabrication Is a System-Level Failure Mode**

Because:

[  
F =  
f(  
\text{architecture},  
\text{training},  
\text{reward},  
\text{context},  
\text{retrieval},  
\text{decoding},  
\text{runtime},  
\text{interface},  
\text{evaluation}  
)  
]

Architecture is one term in the function, not the entire equation.

# Important word-level corrections

## `Preserve`

In:

```text
Preserve all source citations.
```

`preserve` is an activation `[A]`.

It is dual only when nominalised:

```text
Preservation requirement: all source citations.
```

## `Return`

In:

```text
Return exactly one JSON object.
```

`return` is an activation `[A]`, not a signal.

## `Format`

It is genuinely dual:

```text
Output format: JSON.       # signal
Format the result as JSON. # activation
```

## `Verify` and `validate`

Usually activations. They become signals in headings such as:

```text
Verification requirements
Validation criteria
```

## `Avoid`, `prevent`, `protect`, `enforce`

These are often **false activators** unless supplied with an object, mechanism, and failure response.

Weak:

```text
Prevent hallucination.
```

Operational:

```text
For every material factual claim, retrieve a primary source.
If no source supports it, omit the claim and list it as unresolved.
```

## `Confidence`

`Confidence: 92%` can invite invented precision.

Prefer:

```text
Evidence status:
- directly supported
- inferred
- disputed
- unverified
```

That transforms confidence theatre into provenance.

## `Compress`

Compression should carry a preservation clause:

```text
Compress the explanation without removing qualifications,
exceptions, evidence links, or unresolved uncertainties.
```

Otherwise it can activate exactly the complexity loss your framework is designed to catch.
